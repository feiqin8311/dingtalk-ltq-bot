# 单聊业务选择与跟踪号查询模式设计

## 背景

当前机器人只有一套以 FBA 为中心的处理链路：

1. 用户发送 FBA 编号。
2. 机器人查询钉钉表格记录。
3. 根据记录中的货代公司决定查询平台。
4. 返回基础订单信息和物流轨迹。

新需求不是替换现有逻辑，而是在单聊场景中新增第二套独立业务：

- `FBA查询`：保留现有逻辑。
- `跟踪号查询`：不查钉钉表格，直接按跟踪号前缀选择平台官网查询。

两套业务需要通过单聊中的业务选择菜单进行切换，并支持持续模式，直到用户回复 `重置` 才退出当前业务。

## 目标

- 在单聊中引入明确的业务选择入口。
- 保留现有 FBA 查询逻辑不变，避免把新规则混入原有货代平台判定。
- 新增一套按跟踪号前缀分流的平台查询逻辑。
- 支持用户在一次选择后持续发送多条消息，重复执行同类查询。
- 支持用户通过 `重置` 放弃当前业务并重新选择。

## 非目标

- 不改造群聊流程。
- 不修改现有钉钉表格字段结构。
- 不引入账号密码登录的新平台。
- 不在本次设计中重构整个消息路由架构。

## 用户交互

### 菜单文案

机器人在单聊未选择业务时，返回固定菜单：

```text
已重置当前选择。
请选择要办理的业务：
1. FBA查询
2. 跟踪号查询

回复【重置】➡️ 放弃本次并重新选择业务
```

### 状态定义

每个单聊会话维护一个独立状态：

- `menu`：尚未选择业务，等待用户回复 `1` 或 `2`
- `fba`：持续按 FBA 查询逻辑处理消息
- `tracking`：持续按跟踪号查询逻辑处理消息

### 状态切换规则

- 首次进入单聊或状态不存在时：
  - 机器人不执行查询，直接发送菜单。
  - 会话状态置为 `menu`。
- 用户回复 `1`：
  - 会话状态切换到 `fba`。
  - 返回一条提示，说明后续消息将按 FBA 查询处理。
- 用户回复 `2`：
  - 会话状态切换到 `tracking`。
  - 返回一条提示，说明后续消息将按跟踪号查询处理。
- 用户回复 `重置`：
  - 无论当前处于 `menu`、`fba` 还是 `tracking`，都清空当前业务上下文。
  - 重新发送菜单。
  - 会话状态置为 `menu`。
- 用户在 `menu` 状态回复其他内容：
  - 不执行查询。
  - 重新发送菜单。
- 用户在 `fba` 或 `tracking` 状态发送后续消息：
  - 直接按对应业务逻辑执行。
  - 不需要每次重复选择。

## 架构方案

### 推荐方案

在 `main.py` 内新增一个轻量会话状态机，并在现有消息入口前置业务选择判断。

原因：

- 现有消息入口已经集中在 `LogisticsBotHandler`，适合在这里拦截和分流。
- 新需求核心是“单聊状态切换”，而不是重写物流查询实现。
- 现有 FBA 流程可以最大程度复用。
- 这次改动可以控制在入口层和查询层的清晰边界内完成。

### 不采用的方案

1. 直接用消息内容猜测业务，不保存状态
   - 与“持续模式直到重置”冲突。
2. 先重构成完整路由系统再实现功能
   - 成本过高，不适合作为本次迭代的前置条件。

## 组件设计

### 1. 单聊会话状态存储

位置：`main.py`

职责：

- 以单聊会话 ID 为键保存当前业务状态。
- 提供读取、写入、重置状态的简单辅助方法。
- 仅维护最小必要状态，不额外引入数据库或持久化。

建议数据结构：

- `self._conversation_modes: dict[str, str]`

状态值仅允许：

- `menu`
- `fba`
- `tracking`

本状态是内存态。进程重启后，用户需要重新选择业务，这是可接受的。

### 2. 消息入口分流

位置：`LogisticsBotHandler.process` 与 `_handle_text_message`

职责：

- 在现有文本处理逻辑之前，根据单聊状态先决定当前消息是否应进入业务选择流程。
- 保留现有消息去重逻辑。
- 保留现有非文本消息处理逻辑。

行为顺序：

1. 校验消息为文本且内容非空。
2. 识别是否为 `重置`。
3. 读取当前会话模式。
4. 若模式为空或 `menu`：
   - 只处理 `1`、`2`、`重置`
   - 其他内容返回菜单
5. 若模式为 `fba`：
   - 调用现有 FBA 查询流程
6. 若模式为 `tracking`：
   - 调用新增跟踪号查询流程

### 3. FBA 查询流程

保留现有逻辑，不改变核心规则：

1. 把用户消息视为 FBA 编号。
2. 查钉钉表格。
3. 命中记录后按货代公司选择平台。
4. 继续走 `AGL / 平谊 / 堡森 / QQ / 17track / 美通` 等原有能力。

本次只会改变它的进入方式：必须先选中 `FBA查询` 业务后，后续消息才走这一套。

### 4. 跟踪号查询流程

位置：建议在 `main.py` 增加入口函数，在 `logistics_query.py` 增加平台判定与网页查询函数。

职责：

- 不查钉钉表格。
- 把用户消息视为跟踪号。
- 根据跟踪号前缀选择平台。
- 调用对应平台官网查询。
- 未命中特殊前缀时统一回退到英文版 `17track`。

### 5. 跟踪号平台判定

位置：`logistics_query.py`

建议新增函数：

- `decide_tracking_platform(tracking_no: str) -> str`

判定规则按标准化后的跟踪号前缀执行，建议先去空格并转大写：

- `UUS` -> `uniuni`
- `GFUS` -> `gofo`
- `9` -> `usps`
- `1Z0` -> `ups`
- `H00RVA` -> `yuntrack`
- `GV` -> `yuntrack`
- `UK` -> `amazon_uk`
- `TBC` -> `swiship_ca`
- `INTL` -> `swiship_ca`
- `BNI` -> `swiship_ca`
- `TBA` -> `amazon_us`
- 其余 -> `17track_en`

这套函数与现有 `decide_platform(order, explicit_platform)` 完全隔离，避免把“货代公司判定”和“前缀判定”混在一起。

## 查询平台设计

### 通用原则

- 优先使用无需登录的官网查询页。
- 保持和现有网页自动化相同的返回结构：
  - `平台`
  - `查询值`
  - `最新轨迹`
  - `物流轨迹`
  - `错误`
- 若平台抓取失败，应返回结构化错误，而不是让整条消息处理崩溃。
- 对于需要浏览器的平台官网查询，沿用现有浏览器串行执行策略，避免多个 Playwright 任务同时抢占浏览器资源。

## 数据流

### FBA 模式

1. 用户进入单聊。
2. 机器人发送菜单。
3. 用户回复 `1`。
4. 会话进入 `fba` 模式。
5. 用户发送 FBA 编号。
6. 机器人执行现有 FBA 查询链路并回复结果。
7. 用户继续发送 FBA 编号，持续复用该模式。
8. 用户回复 `重置`，返回菜单。

### 跟踪号模式

1. 用户进入单聊。
2. 机器人发送菜单。
3. 用户回复 `2`。
4. 会话进入 `tracking` 模式。
5. 用户发送跟踪号。
6. 机器人按前缀决定平台官网。
7. 机器人执行平台官网查询并回复结果。
8. 用户继续发送跟踪号，持续复用该模式。
9. 用户回复 `重置`，返回菜单。

## 错误处理

- 菜单状态下收到未知输入：
  - 返回菜单，不报错。
- `fba` 模式下收到空文本：
  - 提示发送 FBA 编号。
- `tracking` 模式下收到空文本：
  - 提示发送跟踪号。
- 跟踪号平台官网查询失败：
  - 返回平台名和错误信息。
- 平台无轨迹：
  - 返回“暂无轨迹”或等价空结果文本。
- 状态不存在或异常值：
  - 回退到 `menu` 并重新发送菜单。

## 测试策略

### 单元测试

新增测试应覆盖：

- 单聊首次消息返回菜单
- 回复 `1` 进入 `fba` 模式
- 回复 `2` 进入 `tracking` 模式
- 回复 `重置` 清空模式并返回菜单
- `menu` 状态下未知输入不会触发查询
- `fba` 模式下调用现有 FBA 查询路径
- `tracking` 模式下调用新增跟踪号查询路径
- 跟踪号前缀平台判定函数的全部前缀映射
- 未命中特殊前缀时回退到 `17track_en`

### 集成层验证

在现有 `main.py` 相关测试基础上扩展，重点验证：

- 新状态机不破坏现有去重逻辑
- 新平台查询仍遵守浏览器串行队列
- 现有 QQ 分支与 FBA 平台判定不受影响

## 兼容性与风险

### 兼容性

- 现有 FBA 查询能力保留。
- 现有环境变量体系不需要先行大改。
- 新增平台实现可逐个落地，不要求一次性重构原有查询函数。

### 风险

- 不同平台官网的页面结构稳定性未知，网页选择器需要实测。
- 某些平台可能存在地区跳转、验证码、反爬限制或异步加载较慢的问题。
- 若所有无账号平台都走浏览器自动化，查询耗时会显著增加，需要复用现有串行策略和超时控制。

### 风险应对

- 先把“状态机 + 前缀分流 + 统一查询入口”搭好。
- 各平台官网抓取函数按平台独立封装，单个平台失败不影响整体架构。
- 对无法抓取的平台，保持结构化错误输出，便于后续单点修复。

## 实施边界

本次进入实现时，范围应限定为：

1. 新增单聊业务选择状态机。
2. 保留并接入现有 FBA 查询流程。
3. 新增跟踪号模式与前缀分流。
4. 新增对应测试。

不在本次实现范围内的内容：

1. 群聊支持。
2. 持久化会话状态。
3. 对现有物流平台做大规模重构。
4. 改造钉钉表结构或后台数据源。
